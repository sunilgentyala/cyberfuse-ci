# CyberFuse-CI Architecture

## Overview

CyberFuse-CI is built as three independent, testable layers. Each layer has
a clean input and output interface so you can run them in isolation or swap
components without touching the others.

```
                          CyberFuse-CI Pipeline
                          =====================

  Data Sources            Layer 1                  Layer 2                   Layer 3
  ============            =======                  =======                   =======

  NVD REST API     --->   nvd_connector.py
  STIX/TAXII       --->   stix_connector.py   -->  VulnerabilityEntity   -->  graph_builder.py
  SIEM Syslog/CEF  --->   siem_normalizer.py       (47-dim features)          (OWL graph + SPARQL)
  CVEfixes DB      --->   code_repo_connector.py                              gat_link_predictor.py
                                                                               llm_link_validator.py
                                                                                    |
                                                                                    v
                                                                           adversarial_trainer.py
                                                                           (XGBoost + FGSM)
                                                                                    |
                                                                                    v
                                                                           technique_mapper.py
                                                                           (MITRE ATT&CK FAISS)
                                                                                    |
                                                                                    v
                                                                           Remediation Signal
                                                                           (technique_id, mitigation_id,
                                                                            severity_tier, confidence)
```

## Layer 1: Multi-Source Ingestion and Normalization

Every connector in `connectors/` produces `VulnerabilityEntity` objects
(defined in `connectors/entity_schema.py`). The schema is the contract
between Layer 1 and Layer 2.

### VulnerabilityEntity fields

| Field | Type | Source mapping |
|---|---|---|
| entity_id | str (UUID4) | Generated by framework |
| source | DataSource enum | Which connector produced it |
| source_id | str | CVE ID, STIX UUID, event ID, etc. |
| severity_score | float (0-10) | CVSS base score (normalized for STIX and SIEM) |
| severity_tier | SeverityTier enum | Derived from score via CVSS thresholds |
| affected_component | str | Product, hostname, or repo name |
| affected_versions | list[str] | Version strings or ranges |
| description | str | Free text for NER in Layer 2 |
| cwe_ids | list[str] | CWE-XX identifiers |
| references | list[str] | External URLs |
| published_at | datetime (UTC) | Publication or event timestamp |

### Severity normalization

All sources map to the same 0-10 scale:

- NVD: CVSS v3.1 base score used directly.
- STIX: Confidence field (0-100) divided by 10.
- SIEM: Syslog severity level mapped to fixed scores; keyword signals
  boost the score upward when security-relevant terms appear.
- CVEfixes: CVSS score inherited from the linked CVE record.

## Layer 2: LLM-Augmented Knowledge Graph

The knowledge graph runs on RDFLib with an OWL ontology. The namespace is:
`http://cyberfuse-ci.org/ontology/vulnerability#`

### OWL classes

| Class | Represents |
|---|---|
| Vulnerability | A VulnerabilityEntity individual |
| AffectedComponent | A product or hostname node |
| Weakness | A CWE node |
| ThreatActor | A STIX threat actor (for attribution edges) |

### OWL object properties

| Property | Domain | Range | Meaning |
|---|---|---|---|
| affects | Vulnerability | AffectedComponent | This vulnerability affects this component |
| hasWeakness | Vulnerability | Weakness | This vulnerability is classified under this CWE |
| exploitedBy | Vulnerability | ThreatActor | This vulnerability is exploited by this threat actor |
| mitigatedBy | Vulnerability | Vulnerability | A linked patch or workaround |
| coOccursWith | Vulnerability | Vulnerability | Cross-source co-occurrence signal |

### Knowledge graph construction pipeline

**Step 1: Entity ingestion.** Each VulnerabilityEntity is asserted as an OWL
individual with all data properties populated.

**Step 2: NER and relation extraction.** The BiLSTM-CRF in
`knowledge_graph/ner_extractor.py` runs over the description field of each entity.
It extracts CVE identifiers, product names, vendor names, and CWE categories.
The attention CNN in `knowledge_graph/relation_classifier.py` classifies
edges between extracted entities.

**Step 3: GAT link prediction.** `knowledge_graph/gat_link_predictor.py`
combines TransH-based graph embeddings with BERT textual node vectors in a
Graph Attention Network. It predicts candidate links that are missing from
the initial construction.

**Step 4: LLM link validation.** `knowledge_graph/llm_link_validator.py`
sends candidate links to GPT-4, which generates natural language justifications.
The BERT semantic similarity between justification and existing node descriptions
gates whether the candidate link is inserted. This is an offline batch process
and does not run at inference time.

**Step 5: Cross-source co-occurrence query.** After the graph is built,
`graph_builder.py::find_co_occurrences()` runs a SPARQL query to find
vulnerability nodes that share an `affects` edge to the same component
node but originate from different data sources. These three-source
co-occurrences (CVE + STIX + SIEM) are the highest-confidence signals
for active exploitation.

## Layer 3: Adversarially Hardened Classification and MITRE Mapping

### Feature vector (47 dimensions)

The full list is in `adversarial_training/adversarial_trainer.py::FEATURE_NAMES`.

Feature groups:
- CVSS sub-scores (6 dims)
- CWE category embeddings (10 dims, PCA-reduced from full embedding)
- Graph centrality measures (5 dims)
- Cross-source co-occurrence counts (3 dims)
- STIX indicator temporal recency (2 dims)
- NER entity confidence (5 dims)
- LLM link prediction confidence (3 dims)
- Data source one-hot flags (4 dims)
- Temporal recency and publication age (4 dims)
- Metadata (reference count, description length, CWE count) (3 dims)
- GAT link scores (2 dims)

### Adversarial training

Training uses FGSM with epsilon=0.01. The perturbation is applied only to
continuous features. Categorical features (source one-hot, binary publication
flags) are masked out during perturbation.

The training loop in `adversarial_training/adversarial_trainer.py`:

1. Balance classes with SMOTE.
2. Train a preliminary XGBoost model on the balanced clean data.
3. Use finite-difference FGSM (via `FGSMAttack.perturb_numpy`) to generate
   adversarial versions of `adv_ratio` fraction of the training set.
4. Combine clean and adversarial samples.
5. Train the final XGBoost model on the combined set.
6. Evaluate on a held-out clean test split and an FGSM-perturbed version
   of the same test split.

### MITRE ATT&CK mapping

The mapping uses a FAISS IndexFlatIP (inner product similarity, equivalent to
cosine similarity for L2-normalized vectors). Each ATT&CK technique description
is encoded with `all-MiniLM-L6-v2` from sentence-transformers.

At inference, the vulnerability description is encoded with the same model.
Nearest-neighbor lookup returns the most semantically similar technique with
its tactic and a linked mitigation from the ATT&CK mitigation catalog.

Build the index once with:
```bash
python mitre_mapping/attack_embedding.py --output mitre_mapping/index/
```

## Running the Full Pipeline

```bash
# Step 1: Ingest all sources
python connectors/nvd_connector.py --days 30 --output data/cve.jsonl
python connectors/stix_connector.py --collection enterprise-attack --output data/stix.jsonl

# Step 2: Build knowledge graph
python knowledge_graph/graph_builder.py --inputs data/cve.jsonl data/stix.jsonl --output data/kg.ttl

# Step 3: Build ATT&CK index (once)
python mitre_mapping/attack_embedding.py --output mitre_mapping/index/

# Step 4: Train and evaluate
python evaluation/run_benchmark.py --db /path/to/CVEfixes.db

# Step 5: Adversarial robustness report
python adversarial_training/robustness_eval.py \
    --model evaluation/results/xgboost_classifier.pkl \
    --data evaluation/results/cvefixes_features.csv \
    --epsilon 0.005 0.01 0.02 0.05 \
    --output evaluation/results/adversarial_report.csv
```

## Reproducibility Note

The companion paper's results (Table II and Table III) were produced using:
- CVEfixes dataset downloaded June 2025 (10,077 vulnerable samples)
- NVD API data pulled June 2025 (covering CVEs published 2020-2025)
- ATT&CK v15 STIX bundle
- OpenAI GPT-4 (model version `gpt-4-0125-preview`) for link validation
- XGBoost 2.0.3, scikit-learn 1.4.2, sentence-transformers 3.0.1
- NVIDIA A100 80GB GPU, CUDA 12.1

All datasets except the enterprise SIEM corpus are publicly available.
See README.md for download links.
